# Let the person control recurring reviews

A skill defines the work. The host scheduler supplies execution and time. Do not implement a hidden timer inside the skill or imply installing it starts a service.

1. Reuse the chosen journey, tools, contracts and operating boundaries. Discover an available scheduler and check for the relevant existing task. Do not reactivate a paused task or change an unrelated task without authorization.
2. When scheduling is requested, ask only for missing meaningful choices: cadence, local time or daypart, IANA timezone and destination. Infer a known timezone from the user's context rather than the shell clock. Offer a useful default as an editable choice; follow the host's daypart/exact-time rules. Do not silently convert “morning” into an exact-clock commitment.
3. Put durable task instructions in the schedule prompt: target site, bounded journeys, selected modules, preserved expectations, evidence requirements, private history location, write limits and reporting route. Do not depend on ephemeral scratch paths. Verify required app reads before scheduling according to host rules.
4. Create or update the real task with authorized tools. Retain the returned identifier, confirmed cadence/local time/timezone/destination, prompt/version and enabled state in the private site profile. A proposed cron string or example YAML is not an enabled schedule. Respect daylight-saving behavior of the actual scheduler; GitHub cron uses UTC and needs an explicit conversion/update strategy.
5. Show what is confirmed: “Review scheduled for [actual schedule] in [timezone], delivering to [actual destination]. First unattended run is not yet verified.” Never claim a push notification, email, hosted dashboard or functioning capture without observed support.
6. Support “change the time,” “weekly instead,” “pause,” “resume,” and “stop.” Resolve the relevant task from the saved identifier or actual scheduler inventory; update that task rather than create another. Confirm the returned result, and preserve the person's other preferences. A skill's own edit command is host guidance, not a bundled scheduling API.
7. Inspect the first unattended run and delivery when accessible. Preserve incomplete/failed/stale coverage in the readout. The agent can return discovery evidence when network capture is unavailable, but must not report those event checks as passing. If required access is missing, report the specific setup action and continue independent checks.

For CLI/CI users, the existing `templates/signalcheck-daily.yml` is an execution example. Adapt the cadence in their authorized private site repository, keep evidence private, and test the job/reporting route. Do not put customer site profiles or reports in SignalCheck's public source repository. A host task can instead review an existing runner's authoritative reports after verifying access; it must check freshness and completion rather than equate a green job with clean tracking.

Current ChatGPT scheduling guidance: https://learn.chatgpt.com/docs/automations. Verify current host guidance before creating a schedule. Scheduling access is separate from browser capture, platform access and publication authority.
