# Skill setup design

Apply this guidance while creating or updating skills in the user's Skills project. Use it alongside the relevant skill-creation workflow, not as a substitute for validation, host rules or domain instructions. Delight is a design aim; never claim an emotional outcome has been measured when it has not.

## Start with progress the user can see

Identify the user's actual task, important outcome and first meaningful result. Prefer a result they can use: an observed website failure with a next action, a grounded draft, a validated calculation or a working configuration. A connected account or saved profile is preparation, not automatically value realized.

Reuse known context and prior decisions. Explain the immediate result in one plain sentence. Ask only the next missing decision that blocks useful work; continue independent discovery and preparation. Do not open with a technical questionnaire, ask for IDs the agent can discover or make users repeat information.

## Co-create judgment; automate mechanics

Invite user participation where it changes the result:

1. Choose the priority action/problem.
2. Define intended success in their terms.
3. Resolve business ambiguity or legitimate exceptions.
4. Set scope, test routing and operating boundaries.
5. Correct the agent's readable draft of the rulebook.

Let the agent discover tools, inspect sources, draft selectors/configuration, connect known fields and perform routine implementation. Do not ask the user to do mechanical work merely to manufacture engagement. Offer relevant examples from their actual situation and explain tradeoffs in concrete terms. Preserve existing authorization; ask only when a proposed operation falls outside it or the host requires approval.

Treat current implementation as evidence of what exists, not the definition of what should exist. Separate business intent, observed behavior, inferred cause, proposed action and verified result. Explicitly mark missing evidence and access.

## Deliver an honest first result

Use the smallest meaningful, supported task. Show the result, its evidence, what remains uncertain and a useful next action. Never fabricate a defect, stage a victory or hide a gap to create excitement. Make competence visible through reduced user work and intelligible evidence.

Design for comprehension and momentum without promising delight, ownership, retention or adoption. Those are hypotheses until real users are studied. If measuring setup, retain task, audience, timing boundaries, comparison and actual result; do not invent a benchmark.

## Expand at the point of need

Ask for another integration only when the first task demonstrates its purpose. Explain what access enables and what stays untested without it. Discover actual host capabilities, verify scoped reads and distinguish read, prepare, apply, publish and send operations. A skill install grants neither credentials nor authority.

Draft a readable configuration before JSON or code. Record user choices and source provenance. Persist configuration and evidence in the user's project separately from replaceable installed skill files. Use meaningful checkpoints; avoid repeated confirmation of reversible work already authorized.

## Verify improvements and preserve continuity

Define success before implementation. Prepare concrete, reviewable changes when authorized and rerun the relevant original test afterward. Expand regressions for shared behavior. Keep failure, incomplete observation and unchanged intent separate; changing the test to match a faulty result is not a repair.

Finish with what the user chose, what ran, what the evidence supports, what remains and the next action. Returning users need a change review, not repeated onboarding. Preserve their preferences and operating policy.

## Offer updates and feedback deliberately

When relevant, offer opt-in cadence and channel for updates. Record installed provenance, inspect the diff, prepare a pinned integration, preserve local edits and honor existing authorization. Never silently auto-update or claim a schedule/delivery route exists before verifying it.

Invite one contextual question after a useful result, repair or update. Ask what was missing, confusing or unnecessarily difficult. Avoid early rating requests or repeated prompts. Draft feedback privately with sanitized evidence; send/post only with explicit destination/content authority or an existing request. Never add telemetry or silently subscribe someone.

## Apply Product Language Fit to description updates

Use the current Product Language Fit skill for actual reader-visible descriptions and positioning. Assess exact wording and surrounding support, with all canonical tests in order. Keep an inspectable claim/evidence record proportionate to the surface. Shared utility descriptions may use category language but must not masquerade as unique positioning.

Do not imply bundled integrations, runtime capabilities, autonomous operation, universal coverage, verified outcomes or emotional benefits that the implementation and evidence cannot support. Reevaluate descriptions when scope changes; do not carry old Pass judgments into new copy.

## Validate the setup itself

Forward-test with raw tasks and realistic missing context. Verify that the agent can produce useful progress without leaked answers, unnecessary questions, invented tools or unauthorized writes. Test scripts and native installation. Check failure recovery, incomplete evidence, update conflicts and return visits when applicable.

Read [design basis](references/design-basis.md) for the source distinction and evaluation boundaries. These principles do not replace domain-specific evidence standards.
