# SignalCheck contribution rules

Preserve the real-browser evidence boundary, private evidence handling and explicit site contracts. Treat observed symptoms, inferred causes, proposed fixes, applied changes and verified results as different states. Never weaken expected behavior to make a retest pass.

For every change to product descriptions, README positioning, skill descriptions or package/plugin metadata, run Product Language Fit on the exact changed wording. Keep a concise 12-test evaluation and claim-evidence record in `docs/description-review.md`. Shared utility descriptions need not claim exclusivity. Never imply autonomous hosting, connectors, publishing authority or backend verification that the package does not supply.

Every feature release pushed to main must refresh the description review, even when existing wording is retained. Review the final shipped capabilities and exact descriptions with Product Language Fit, record all twelve named judgments and evidence limitations, and include the review in the same release. Do not claim market validation from editorial review.

Preserve tags and events as SignalCheck’s primary remit. Name the relevant tracking tools in descriptions; treat forms as one supporting source of actions. Setup must discover installed tools and ask which others should be included, retaining the user’s prior choices. Never equate GTM/container loading, script presence, a tracking request, a decoded event and final platform receipt.

Write user-facing descriptions around the problem, the user's next action and an observable result. Put protocol/runtime terminology in technical references; state necessary limits in plain language. Assess Two-second and Voice against the intended reader's knowledge. Technical accuracy alone does not establish comprehension. Retain this reader context when reviewing future updates.

Design setup for a useful first result. Involve users in the choices that need their judgment: priority journey, intended outcomes, legitimate event destinations, test routing and operating boundaries. Let the agent discover and implement the technical details. Explain choices using the actual site. Ask only for missing decisions; retain previous answers. Show one real result early, including gaps. Avoid staged wins, needless integration requests or technical forms that delegate the agent's work to the user.

Use `skills/signalcheck/references/onboarding.md` for the setup flow. Changes that expand actions or permissions need updated host guidance, traceable evidence, verification criteria and appropriate tests. Preserve scope/contract comparison and regression checks. Test code and packaged installation before publishing; run the real Chromium fixture for browser-runner changes.
